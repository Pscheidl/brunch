# Backend contract

Same-origin JSON API under `/api`. Amounts are integer Czech haléře (CZK). Product IDs are positive int64, user/order IDs UUID strings. Errors `{error:string}`. Browser mutations require `X-Brunch-Request: 1`. The content type is `application/json`, with `application/octet-stream` also supported for image uploads. The RSA-verified Teya webhook accepts the provider’s raw JSON without the browser header. Cookies HttpOnly, SameSite=Lax, Secure in production. No permissive CORS.

## Authentication

- POST `/api/auth/request` `{email}` always generic `{message}`. Email link opens `/?login_token=...`. Requesting a link alone does not create an account. A successfully saved first order creates the account automatically. Link redemption reuses that account or creates one if the address has no account yet. Administrators may be created separately by an existing administrator.
- POST `/api/auth/verify` `{token}` -> `{user:{id,email,is_admin}}`, sets session cookie. One use, 15 minute validity.
- GET `/api/auth/me` -> `{user:{id,email,is_admin}}` or 401.
- POST `/api/auth/logout` `{}` -> `{ok:true}` clears session.
- POST `/api/admin/auth/login` `{email,password}` -> `{user:{id,email,is_admin:true}}` and a 12-hour session cookie. Invalid login has a generic error. Account and global rate limits run before password hashing. Admin sessions require password authentication as well as the current database role. Customer magic links never create an administrative session, including for the same email.

Administrator passwords use Argon2id with 19 MiB memory, two iterations, one lane and a fresh random 16-byte salt for every password. The PHC string stores the hash, salt and parameters in PostgreSQL, never in an API response. Passwords accept 12 to 128 Unicode characters, at most 512 UTF-8 bytes. Hash work is bounded to two concurrent operations. Administrator identities and roles are not read from environment configuration.

## Shop

- GET `/api/products` -> array of products `{id,name,description,category,tag,weight,price_cents,vegan,ingredients,allergens,image,active,stock,minimum_quantity,version}`. `image` relative asset URL or empty. `stock` nullable int (null unlimited). Only active products. `minimum_quantity` is 0–99, with zero allowing any orderable quantity. Checkout enforces the minimum against current product data. Product creation defaults the minimum to 0. Product updates preserve the stored value when the field is omitted.
- GET `/api/settings` -> `{delivery_fee_cents,free_delivery_from_cents,delivery_postal_codes:[string],online_payment_enabled:bool}` threshold nullable. Postal codes are sorted canonical five-digit strings for active delivery areas. An empty list blocks new orders.
- GET `/api/delivery-options` -> `{dates:[{value:"YYYY-MM-DD",label:string}],slots:[string],postal_slots:{[postal_code]:[string]}}`. The first date is the earliest selectable day in Europe/Prague. The three date suggestions remain available for existing clients. The calendar and checkout accept any future working day, excluding weekends and Czech public holidays. Active areas use the shop's `slots` unless `postal_slots` contains an override.
- POST `/api/orders` -> `{id,number,status,payment_method,subtotal_cents,delivery_fee_cents,total_cents,...}` with body `{idempotency_key:uuid,email,name,phone,organization?,street,city,postal_code,notes?,delivery_date:"YYYY-MM-DD",delivery_slot,payment_method:"card"|"card_on_delivery"|"cash_on_delivery",items:[{product_id,quantity}],expected_total_cents}`. Name, phone, email, street, city and postal code required for new orders. Reject outdated expected total with 409. Prices and delivery recalculated server-side. Snapshots saved transactionally with stock. Delivery orders start `new` and queue business/customer confirmations. Online orders start `awaiting_payment`, queue a customer pending notice and a persistent payment attempt in the same transaction. Business fulfilment notification waits for verified payment. Same idempotency key and payload replays existing order, altered payload 409. Every accepted order attaches to the account for its normalized email, creating a customer account in the same transaction if needed. This applies without authentication and when the signed-in account uses another email. Account creation does not create a session, grant administrative rights or expose order history. Migration 0020 also links previous guest orders and creates missing customer accounts.
- Checkout validates five-digit Czech postal codes and membership in active delivery areas, 1–50 distinct products, 1–99 units per product, available requested delivery date/slot, and total up to 1,000,000,000 haléře. All Unicode whitespace and U+FEFF are removed from postal codes before validation, storage and idempotency comparison. Other characters are rejected. Inactive or unconfigured postal codes return 400 without creating an order, reserving stock or queuing email. Successful idempotent replays remain available even if the area has since been deactivated. Name and optional organization are at most 200 characters, phone 40, street 250, city 100 and notes 2,000. New accepted orders are limited to 20 per email and 500 globally per hour with HTTP 429. Idempotent replays do not consume these limits.
- POST `/api/address-suggestions` with `{text}` (3–100 characters) returns up to six RÚIAN address matches as `[{label,street,city,postal_code}]`. The server forwards only the address search text to the ČÚZK RÚIAN locator. Unavailable or busy lookup returns 503. Checkout accepts a manually entered address independently of lookup results.
- GET `/api/orders/mine` -> array of up to 100 own orders, newest first, after email authentication. Includes orders submitted without login under the same normalized email. Entering an email in checkout does not grant access to this endpoint.

## Images

- POST `/api/admin/images` (admin only) raw file body with `Content-Type: application/octet-stream` (legacy JSON `{filename,content_base64}` also accepted) -> `{url:"/api/images/{uuid}"}`. Source JPEG/PNG/WebP up to 40 MiB, 16,384 px per side and 52 megapixels. Server fits the image within 1,440 × 1,440 px, applies EXIF orientation, preserves transparency and stores immutable JPEG (quality 88) or PNG without source metadata in PostgreSQL.
- GET `/api/images/{uuid}` publicly returns sanitized JPEG/PNG, immutable one-year cache and ETag support.

## Admin (session is_admin required for every endpoint)

- GET `/api/admin/administrators` -> `{administrators:[{id,email}]}`.
- POST `/api/admin/administrators` `{email,password}` -> `{administrator:{id,email}}`. Email is normalized. Existing customer accounts are promoted without replacing account data. Existing sessions are revoked. Duplicate administrators return 409.
- DELETE `/api/admin/administrators` `{email}` -> `{ok:true}`. Removes the role, password hash and all sessions, preserving the customer account and orders. Unknown administrator returns 404. The final administrator cannot be removed, returning 409 even during concurrent requests. Self-removal is permitted when another administrator remains.
- PUT `/api/admin/administrators/password` `{email,password}` -> `{ok:true}`. Resets an existing administrator password and revokes all target sessions, including the caller's session if changing their own password.
- Administrator membership and password changes serialize under a shared database transaction lock. The actor's current password-authenticated session is checked again after the lock is acquired. Login rechecks the role and password hash after verification before creating a session.
- GET `/api/admin/categories` -> array of `{id,name,version,product_count}`, including empty categories.
- POST `/api/admin/categories` accepts `{name}`, PUT `/api/admin/categories/{id}` accepts `{name,version}`, DELETE accepts `{version}`. Each mutation returns `{id}`. Names accept up to 80 characters. Renaming updates assigned products. Deleting leaves all products intact with the empty category, including archived products. Stale category edits return 409.
- GET `/api/admin/products` -> array incl inactive.
- POST `/api/admin/products` product fields (id/version omitted) -> product
- PUT `/api/admin/products/{id}` product fields incl `version` -> product, optimistic conflict 409
- GET `/api/admin/products/{id}/prices` -> array `{id,price_cents,created_at,changed_by}`
- GET `/api/admin/orders?status=&q=&delivery_date=YYYY-MM-DD&page=1` -> `{orders:[...],total,page}` 50 per page. Optional `delivery_date` selects the stored delivery day, independent of creation time, and combines with status/search. Empty or omitted date includes every day, invalid dates or noncanonical formats return 400. Count and rows use the same filters, with stable `created_at DESC,id DESC` ordering. orders contain snapshot `items:[{product_id,name,quantity,unit_price_cents,total_cents}]`, delivery/contact data, `version`, `payment_status` and timestamps.
- GET `/api/admin/orders/{id}` -> order detail incl items and `history:[{status,payment_status,created_at,changed_by}]`
- PATCH `/api/admin/orders/{id}` `{status:"awaiting_payment"|"new"|"confirmed"|"out_for_delivery"|"delivered"|"cancelled",payment_status:"unpaid"|"paid",version}` -> order. Sequential flow is `new → confirmed → out_for_delivery → delivered`. Online payment can never be manually marked paid and an unpaid online order cannot advance. Only verified terminal failed/expired sessions allow unpaid online cancellation. Delivery payment can be marked paid only during `out_for_delivery` or `delivered`, and `delivered` requires `paid`. Stock restored once on cancellation. Delivered, cancelled and expired orders are terminal. Cancellation is available before delivery only while unpaid. Paid cannot revert to unpaid, and paid cancellation requires future refund handling. Each actual status change also queues a customer email transactionally.
- POST `/api/admin/orders/bulk-status` takes `{orders:[{id,version}],from_status,status,confirm_payments?}`. Applies the same transition to up to 50 same-status orders in one transaction. Unpaid cash/card-on-delivery orders require explicit confirmation to mark them delivered.
- GET and PUT `/api/admin/invoice-supplier` return the issuer’s `{name,address,company_id,tax_id,registration,vat_payer,version}`. PUT accepts the same fields. Name, address and company ID are required, as is tax ID for VAT payers. A stale version returns 409.
- GET `/api/admin/orders/{id}/invoice` returns the stored document or `null`. POST issues one invoice per order with `{supplier_version,customer_name,customer_address,customer_company_id,customer_tax_id,supply_date,due_date,vat_rates}`. Use empty strings for optional customer IDs and ISO dates for supply and due dates. A VAT payer supplies rates keyed by product ID, plus `delivery` for a nonzero delivery fee. Rates are hundredths of a percentage point (e.g. `1200` for 12%). Other suppliers send `{}` for `vat_rates`. The server snapshots order prices, supplier and customer details, tax amounts, payment state, dates and invoice number. Concurrent issuance and subsequent POSTs return the stored document. The admin displays this document for printing or saving as PDF.
- GET `/api/admin/settings` -> `{delivery_fee_cents,free_delivery_from_cents,order_email,additional_order_emails:string[],delivery_slots,version}`. The primary `order_email` remains the customer-facing contact. Additional addresses are private staff recipients. PUT accepts an optional `additional_order_emails` array, omitted or null preserves the stored list and an empty array clears it. Addresses are trimmed, lowercased and deduplicated against the primary address, with at most 20 unique recipients in total. Each staff recipient gets a separate transactional outbox entry for a new payable-on-delivery order, a verified paid online order or a late payment requiring review. Public settings omit both address fields.
- PUT `/api/admin/settings` same fields -> settings (version conflict 409). Delivery slots are a nonempty array of nonoverlapping, same-day time ranges, such as `["07:00–09:00","10:00–12:30"]`. Omitting the field preserves the current schedule.
- GET `/api/admin/delivery-areas` -> array `{id,postal_code,label,active,delivery_slots,version}`, including inactive areas.
- POST `/api/admin/delivery-areas` `{postal_code,label?,active?,delivery_slots?}` -> area. Label defaults to empty and is at most 100 characters, active defaults to true. Canonical postal codes are unique even across inactive areas. Duplicates return 409.
- PUT `/api/admin/delivery-areas/{id}` `{postal_code,label?,active?,delivery_slots?,version}` -> area, stale version or duplicate code returns 409. Set `delivery_slots` to null to inherit the shop-wide schedule, or supply a replacement array. Omitting the key leaves the override unchanged. Deactivate with `active:false`, reactivate with `active:true`. Updates serialize against checkout through the shared shop settings row so an accepted order uses a consistent delivery configuration.
- GET `/api/admin/customers?page=1` -> `{customers:[{id,email,is_admin,created_at,order_count}],total,page}`. Includes automatically created accounts and all orders attached by email. The presence of an account does not establish that its email has been verified.
- GET `/api/admin/mail` -> array `{id,to_email,subject,status,attempts,last_error,created_at,sent_at,can_retry}` latest 100, status pending/sent/failed
- GET `/api/admin/mail/broadcast` -> `{recipient_count}` counts distinct normalized e-mails from submitted orders, including orders submitted without login.
- POST `/api/admin/mail/broadcast` `{idempotency_key:uuid,subject,body}` -> `{recipient_count}`. Queues one private plain-text message per distinct order address at send time. The subject is a single line of up to 200 characters, the body accepts up to 12,000 characters. The same administrator can replay the same key and text to recover the original result. Changed content returns 409.
- POST `/api/admin/mail/{id}/retry` `{}` -> `{ok:true}` requeues failed email

## Shared server interfaces

`AppState { pool: PgPool, config: Arc<Config> }` in crate root, `ApiError` implements IntoResponse with constructors `bad_request`, `unauthorized`, `forbidden`, `conflict`, `not_found`, From sqlx::Error. `type ApiResult<T> = Result<T,ApiError>`.
`auth::current_user(&AppState,&HeaderMap) -> ApiResult<Option<User>>`, `auth::require_user(...) -> ApiResult<User>`, `auth::require_admin(...) -> ApiResult<User>`. User `{id:Uuid,email:String,is_admin:bool}`.
`mail::enqueue(&mut PgConnection,to:&str,subject:&str,body:&str) -> ApiResult<()>` to insert outbox within transaction. Config fields `public_url`, `order_email` etc.
`commerce::routes() -> Router<AppState>` includes full `/api/...` routes. `commerce::seed(&PgPool,&str)` inserts default settings and six products only when empty, no production data overrides.

## Teya Hosted Checkout

- POST `/api/orders/{id}/payment` body `{idempotency_key:uuid}` returns `{status,payment_status,checkout_url:string|null,payment_state,expires_at}`. Original checkout UUID is an unguessable capability, verified together with order ID. No personal data or secrets returned. No provider request triggered by this endpoint. Wrong key/order returns 404. A checkout URL is returned only for unpaid awaiting-payment orders with ready sessions and a deadline in the future.
- POST `/api/payments/teya/webhook` accepts exact raw JSON plus `x-teya-signature` Base64 RSA/SHA-256. This one POST route is exempt from browser CSRF headers. Invalid signatures return 401, mismatches fail, valid notifications return 204 only after database commit. Duplicate bodies do not create additional notifications. No success is inferred directly from the body. A worker verifies the session through the authenticated Teya API.
- GET `/api/admin/orders/{id}` additionally includes `online_payment:{state,expires_at,checked_at,last_error,cancellable,receipt}` for online orders. `receipt` is null before verified payment, otherwise `{transaction_id,session_id,amount_cents,currency,verified_at}` read from the persistent `payment_receipts` table. Late payments on closed orders retain this receipt alongside the review warning. Operational metadata and receipt identifiers are omitted from public creation, replay, account and payment-status responses. Credentials and checkout URLs are never in this object.
- Local payment states: `pending`, `ready`, `paid`, `failed`, `expired`, `review`. Order/payment state, receipt and email queue commit atomically. Persistent leases, provider idempotency UUIDs and unique transaction/session receipts protect restart and concurrent handling.
- Hosted checkout returns to `/?payment_return=<order UUID>`. This is a UI hint only. Original checkout capability remains in session storage, never in the return URL. The browser must fetch payment state and must not create a new payment when confirmation is delayed.

See [teya-payments.md](teya-payments.md) for credential storage, operational recovery, retry boundaries and required provider staging validation.

### Local online-order expiration

`ONLINE_PAYMENT_TIMEOUT_MINUTES` defaults to 60 and accepts integer 1..1440. On creation, `payment_attempts.expires_at` is persisted from order creation time. All online order responses include `payment_expires_at`. Settings changes and restarts do not extend existing deadlines. Migration of previously created online orders uses the original creation time plus one hour.

Independent maintenance every second expires due unpaid online orders, transactionally restoring reserved stock once and queuing one customer message. This runs even without Teya connectivity or configured credentials. Delivery-payment orders and verified paid orders are excluded. Status `expired` is terminal and cannot be assigned manually through admin PATCH. During application/database downtime, deadlines are processed after recovery.

Reconciliation checks the deadline while holding order/payment locks before accepting success. A late verified payment retains a unique receipt, leaves the order closed, sets payment process `review` and queues alerts once to the customer and shop. No further fulfilment or stock reservation occurs. Known provider sessions remain eligible for verification, but no new session is created after the local deadline. Teya's separate Hosted Checkout session lifetime remains 15 minutes.
